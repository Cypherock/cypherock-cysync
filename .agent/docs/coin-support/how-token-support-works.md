# How Token Support Works

This document explains how **fungible tokens** (ERC-20, SPL, TRC-20, ICRC, Canton instruments) are handled in CySync. It assumes you already understand the native-coin flow — see [how-coin-support-works.md](how-coin-support-works.md). Most operations behave identically to native coins; this doc focuses on **where tokens differ**.

Families that support tokens today:

| Family | Token standard | Reference package |
|---|---|---|
| EVM | ERC-20 | [packages/coin-support-evm](../../../packages/coin-support-evm/) |
| Solana | SPL | [packages/coin-support-solana](../../../packages/coin-support-solana/) |
| Tron | TRC-20 | [packages/coin-support-tron](../../../packages/coin-support-tron/) |
| ICP | ICRC | [packages/coin-support-icp](../../../packages/coin-support-icp/) |
| Canton | Domain-specific (instruments) | [packages/coin-support-canton](../../../packages/coin-support-canton/) |

---

## 1. The token model (concepts that recur in every family)

### 1.1 `assetId` format

For native coins, `assetId === parentAssetId === coinId` (see [how-coin-support-works.md](how-coin-support-works.md#6-coin-metadata-the-coins-package)).

For tokens, two fields are stored on every account / transaction / price row:

| Field | Value |
|---|---|
| `parentAssetId` | The native coin's ID (e.g. `ethereum`) |
| `assetId` | Token's compound ID: `{parentAssetId}:{tokenId}[\|{version}]` (e.g. `ethereum:uniswap`) |

The version suffix is added by the automation scripts only when a CoinGecko ID is reused across migrated contracts on the same chain. See [packages/coins/src/evm/token.ts:35-43](../../../packages/coins/src/evm/token.ts#L35-L43) for the canonical `createErc20AssetId` factory; the other families have identical helpers (`createSplAssetId`, `createTrc20AssetId`, `createIcrcAssetId`, `createCantonInstrumentAssetId`).

### 1.2 Token account = sub-account

A token account is a row in the same `account` repo as a native account, but with:

- `type = AccountTypeMap.subAccount`
- `parentAccountId` pointing at the native account
- `assetId` set to the token's compound ID
- `parentAssetId` set to the chain's coin ID
- `xpubOrAddress` typically **inherited from the parent native account** (the wallet's public key/address is the same; the token "address" is derived per-chain on demand — see §3.1)

A wallet holding ETH and USDC on Ethereum therefore has:

```
Account A:  type=account,   assetId=ethereum,                parentAssetId=ethereum
Account B:  type=subAccount, assetId=ethereum:usd-coin,       parentAssetId=ethereum,   parentAccountId=A
```

### 1.3 Token metadata loading

Each token-supporting family has a `token.ts` file in [packages/coins/src/{family}/](../../../packages/coins/src/) that:

1. Imports the corresponding JSON list (`erc20.json`, `spl.json`, `trc20.json`, `icrc.json`, `instruments.json`).
2. Walks every entry, validates required fields (contract address, decimals, …), and constructs a typed token object.
3. Produces **two indexes** per parent coin: `tokens` (keyed by assetId) and `tokensByContract` (keyed by lowercase contract address) so the sync path can resolve tokens by either.

| Family | Token interface | Validated extra fields |
|---|---|---|
| EVM | `IEvmErc20Token` | `parentId`, `address` |
| Solana | `ISolanaSplToken` | `parentId`, `address`, `decimals` |
| Tron | `ITronTrc20Token` | `parentId`, `address` |
| ICP | `IIcpIcrcToken` | `parentId`, `address`, `decimals`, `dashboardRoute`, `canisters.{ledger,index}` |
| Canton | `ICantonToken` | `parentId`, `address`, `decimals`, `instrument.{id,admin}` |

The JSON files are generated by `packages/automation-scripts` — see §6.

## 2. The `CoinSupport` contract for tokens

There is **no separate `TokenSupport` interface**. The same `CoinSupport` methods documented in [how-coin-support-works.md §2](how-coin-support-works.md#2-the-coinsupport-contract) handle both native and token cases; the implementation branches internally on whether the operation's account is `type === AccountTypeMap.subAccount`.

What changes per operation is summarised below; deep dives follow in §3.

| Operation | Native coin | Token (sub-account) |
|---|---|---|
| `createAccounts` | Discovers parent accounts via derivation walk | Token accounts are typically auto-discovered by `syncAccount`, not by `createAccounts`. EVM also has explicit token-account creation via the Add Token dialog. |
| `syncAccount` | Fetches balance + txn history from indexer | For native account: scans contract-transfer logs and auto-creates sub-accounts for any unknown token. For token sub-account: fetches the token-specific balance and transaction history. |
| `initializeTransaction` | Fetches gas/nonce/UTXOs | Same as native, **plus** token-specific data (rent for new SPL ATAs, energy estimate for TRC-20, ledger canister for ICRC) |
| `prepareTransaction` | Validates amount/fee against native balance | Validates amount against the **token** balance; validates fee against the **parent native** balance |
| `signTransaction` | Signs native transfer | Signs a contract call / canister call / instruction with token-specific payload |
| `broadcastTransaction` | Posts native tx | Same endpoint; the token's contract address / canister ID is embedded in the payload |
| `validateAddress` | Same per chain | Same per chain — token transfers use the chain's native address format |
| `receive` | Returns next derived address | Returns the parent's address (with chain-specific derivation, e.g. SPL ATA, for the displayed address) |
| `syncPrices` / `syncPriceHistories` | Per `(parentAssetId, assetId)` — `getCoinIds(db)` returns one entry per coin & token, prices are fetched for all in batches |
| `getCoinAllocations` | Aggregates by `(parentAssetId, assetId)` | Same — tokens appear as their own allocation entries |
| `getAccountHistory` | Replays transactions vs. price history | Same; some chains pay fees from the **parent** account, which the utility accounts for |
| `getExplorerLink` | Native explorer URL | Native explorer URL (same path; contract address embedded for tokens on some chains) |

## 3. Per-operation deep dive (token differences)

### 3.1 Token account creation & discovery

Token accounts are almost always **created reactively by `syncAccount`** (not by `createAccounts`). When the native account's sync sees a transfer involving a token contract the wallet doesn't yet track, it creates the sub-account on the fly.

The pattern is consistent but the trigger differs:

| Family | Discovery mechanism | Key code |
|---|---|---|
| EVM | `syncAccount` calls `getContractTransactions()` per known token; `mapContractTransactionForDb()` creates a new sub-account whenever it sees a contract address not yet tracked. | [packages/coin-support-evm/src/services/helpers/contractTransactions.ts:17-74](../../../packages/coin-support-evm/src/services/helpers/contractTransactions.ts#L17-L74) |
| Solana | `syncAccount` scans the parent account's tx feed; `mapTokenTransactionsForDb()` parses SPL transfers and creates sub-accounts using `deriveAssociatedTokenAddress()`. | [packages/coin-support-solana/src/services/helpers/transactions.ts:62-74](../../../packages/coin-support-solana/src/services/helpers/transactions.ts#L62-L74) and [`utils/deriveTokenAddress.ts:4-17`](../../../packages/coin-support-solana/src/utils/deriveTokenAddress.ts#L4-L17) |
| Tron | TRC-20 events extracted from tx logs by the parent's sync; token object resolved via `tronCoinList[parentId].tokensByContract[contractAddress]`. | [packages/coin-support-tron/src/operations/syncAccount/index.ts:144-152](../../../packages/coin-support-tron/src/operations/syncAccount/index.ts#L144-L152) |
| ICP | More proactive: token sub-accounts are created when the user adds the token via the AddToken dialog. `syncAccount` for the parent then walks each enabled token's `canisters.ledger` and `canisters.index`. | [packages/coin-support-icp/src/operations/syncAccount/index.ts:117-136](../../../packages/coin-support-icp/src/operations/syncAccount/index.ts#L117-L136) |
| Canton | Proactive: instruments are auto-discovered from the canister state when `syncAccount` runs on the parent; `getTokenObject()` / `getCantonTokenAccount()` insert the sub-account. | [packages/coin-support-canton/src/operations/syncAccount/index.ts:79-111](../../../packages/coin-support-canton/src/operations/syncAccount/index.ts#L79-L111) |

#### Token address derivation

| Family | Token "address" |
|---|---|
| EVM | Same EOA address as the parent native account |
| Solana | **Associated Token Account (ATA)** — `getAssociatedTokenAddressSync(mintAddress, ownerPublicKey)`. The display address shown in the Receive dialog is the ATA, **not** the SOL address. |
| Tron | Same Tron base58 address as the parent (TRC-20 transfers use the same address) |
| ICP | Derived principal from `extraData.publicKey` — see `derivePrincipalIdFromPrincipal()` in [packages/coin-support-icp/src/operations/syncAccount/index.ts](../../../packages/coin-support-icp/src/operations/syncAccount/index.ts) |
| Canton | Inherits parent's party address; instrument ID + admin distinguish the token |

### 3.2 syncAccount — balance fetch

| Family | Native balance | Token balance |
|---|---|---|
| EVM | RPC eth_getBalance via Cypherock proxy | `getContractBalance()` — RPC `eth_call` to `balanceOf(address)` per contract |
| Solana | `getBalance(address)` → `lamports` | `getTokenBalance(derivedATA)` → `tokenAmount.amount` ([packages/coin-support-solana/src/services/api/wallet.ts:32-44](../../../packages/coin-support-solana/src/services/api/wallet.ts#L32-L44)) |
| Tron | RPC direct | `triggerConstantContractCall()` invoking `balanceOf(address)`, hex result → balance ([packages/coin-support-tron/src/services/api/account.ts:41-66](../../../packages/coin-support-tron/src/services/api/account.ts#L41-L66)) |
| ICP | ICP ledger query | Per-token `getTokenBalance(principalId, tokenDetails.canisters.ledger)` |
| Canton | Parent state query | Per-instrument balance aggregation |

The `syncAccount` factory in `coin-support-utils` ([how-coin-support-works.md §4.2](how-coin-support-works.md#42-syncaccount)) is reused for both — the family-supplied `getAddressDetails()` callback dispatches on `account.type`.

### 3.3 syncAccount — onNewAccounts hook

When `syncAccount` discovers a new token, it must trigger price + history sync for that token. This is what the `onNewAccounts` callback in the sync observable is for. Look for `onNewAccounts` references in `operations/syncAccount/index.ts` of each family (Solana, EVM, Tron, ICP, Canton all use this hook).

### 3.4 prepareTransaction — token transfer encoding

This is where the chains diverge most. Each chain encodes the token transfer differently:

**EVM (ERC-20).** [packages/coin-support-evm/src/operations/prepareTransaction/index.ts:46-75](../../../packages/coin-support-evm/src/operations/prepareTransaction/index.ts#L46-L75):

```ts
// For ERC-20: encode transfer(to, amount) into the data field
// The on-chain tx value is 0; the actual transfer is the contract call
if (isTokenTransfer) {
  data = contract.methods.transfer(output.address, amountInSmallestUnit).encodeABI();
  txValue = '0';
  to = tokenContract.address;
}
gasLimit = await estimateGas({ from, to, data, value: txValue });
fee = gasLimit * gasPrice;
```

**Solana (SPL).** [packages/coin-support-solana/src/operations/prepareTransaction/index.ts:148-178](../../../packages/coin-support-solana/src/operations/prepareTransaction/index.ts#L148-L178):

```ts
// If recipient has no ATA, prepend a createAccount instruction (rent-exempt funding)
const doesExist = await checkIfRecipientTokenAccountExists(output.address, coin.id, mint);
if (!doesExist) {
  instructions.push({ type: InstructionType.createAccount, recipient, mintAddress });
}
// Then transferChecked (vs. transfer for native SOL)
instructions.push({
  type: InstructionType.transferChecked,
  amount, recipient, mintAddress, decimals,
});
```

**Tron (TRC-20).** [packages/coin-support-tron/src/utils/transaction.ts:24-66](../../../packages/coin-support-tron/src/utils/transaction.ts#L24-L66):

```ts
if (params.tokenDetails) {
  const txn = (await tronWeb.transactionBuilder.triggerSmartContract(
    params.tokenDetails.address,            // TRC-20 contract address
    'transfer(address,uint256)',
    { feeLimit, callValue: 0 },
    [{ type: 'address', value: params.to }, { type: 'uint256', value: amount }],
    tronWeb.address.toHex(params.from),
  )).transaction;
}
// Token energy estimation differs from native bandwidth/energy calculation
```

**ICP (ICRC).** [packages/coin-support-icp/src/operations/prepareTransaction/index.ts:57-72](../../../packages/coin-support-icp/src/operations/prepareTransaction/index.ts#L57-L72):

```ts
const isTokenAccount = account.type === AccountTypeMap.subAccount;
if (isTokenAccount) {
  // Token transfers route to a different ledger canister; the principal must be re-derived
  myAddress = Principal.from(derivePrincipal(account.extraData.publicKey)).toText();
}
// Memo is invalid for token transfers — must be cleared
const isInvalidMemo = output.memo !== undefined &&
  (isTokenAccount || BigNumber(output.memo).gte(MAX_UINT64));
```

**Canton.** [packages/coin-support-canton/src/operations/prepareTransaction/index.ts:46-100](../../../packages/coin-support-canton/src/operations/prepareTransaction/index.ts#L46-L100):

```ts
let instrument: ICantonInstrument;
let decimals: number;
if (isTokenAccount) {
  const tokenDetails = cantonCoinList[parentAssetId].tokens[assetId];
  instrument = tokenDetails.instrument;
  decimals = tokenDetails.decimals;
}
// UTXOs come from the parent native account; instrument identifies the token
const utxos = selectUtxos(targetAmount, sortedUtxos);
```

### 3.5 prepareTransaction — fee accounting

A key cross-chain pattern: **fees are paid by the parent native account, not the token sub-account**.

| Family | Fee source |
|---|---|
| EVM | Parent ETH (or chain-native) account |
| Solana | Parent SOL account |
| Tron | Parent TRX account (energy + bandwidth deducted) |
| ICP | The token's ledger charges its own flat fee deducted from the sending principal |
| Canton | Parent account's UTXOs |

The validation flags in `IPreparedTransaction` therefore need to check:

1. `hasEnoughBalance` against the **token** balance (for the transfer amount).
2. `hasEnoughBalanceForFee` (or equivalent) against the **parent** balance (for gas/fees).

### 3.6 signTransaction

The device-signing flow is **structurally identical** to native — the same `makeSignTransactionsObservable` factory, the same `INIT → CONFIRMED → VERIFIED → CARD_TAPPED` event sequence (see [how-coin-support-works.md §4.5](how-coin-support-works.md#45-signtransaction)).

What differs is what the family-specific `signTransactionFromDevice` callback puts into the SDK payload:

- **Solana** ([packages/coin-support-solana/src/operations/signTransaction/index.ts:74-93](../../../packages/coin-support-solana/src/operations/signTransaction/index.ts#L74-L93)) — passes an extra `tokenData.recipientAddress` field so the device firmware knows the displayed amount maps to a token transfer:
  ```ts
  if (tokenDetails) {
    signTxnParams.tokenData = { recipientAddress: base58Decode(output.address) };
  }
  ```
- **EVM** — the calldata field already contains the ABI-encoded `transfer(...)` call, so the device sees the calldata and the SDK firmware parses it for the confirmation screen.
- **Tron** — smart-contract transaction payload encodes the call selector and parameters.
- **ICP** — payload includes the destination ledger canister ID.
- **Canton** — instrument identifier travels in the payload.

The derivation path is **the same as the parent's** in every case (token transfers are signed with the parent's key).

### 3.7 broadcastTransaction

Same endpoint as native. Tokens reuse the family's broadcast service (`services/broadcast.ts`) verbatim — the signed payload's structure already differentiates a token transfer from a native one.

### 3.8 syncPrices / syncPriceHistories

The `getCoinIds(db)` helper that each family supplies returns one entry per held coin **and** token:

```ts
// e.g. packages/coin-support-solana/src/utils/getCoinIds.ts:5-18
const accounts = await db.account.getAll({ familyId });
return accounts.map(a => ({
  assetId:       a.assetId,         // 'solana' or 'solana:usd-coin'
  parentAssetId: a.parentAssetId,   // 'solana'
}));
```

The shared `createSyncPricesObservable` then batches up to 20 of these and hits the CoinGecko proxy. Tokens get prices the same way native coins do — keyed by `coinGeckoId` resolved through `getAsset(db, { assetId, parentAssetId })`.

### 3.9 getCoinAllocations & getAccountHistory

Both factories ([how-coin-support-works.md §4.8](how-coin-support-works.md#48-getcoinallocations--getaccounthistory)) already group by `(parentAssetId, assetId)`, so tokens are first-class. The notable token-specific branch is in `getAccountHistory` for **ICP**: the fee on a token transfer is deducted from the token account itself in some flows, while on EVM/Solana/Tron the fee comes from the parent — the utility handles both via the transaction's `fees` field.

### 3.10 receive

Native chains return `account.xpubOrAddress`. Token-specific receive logic only matters when the **displayed deposit address differs from the parent's address**:

- **Solana SPL** — the UI must display the derived ATA, not the parent SOL address (otherwise deposits won't credit the right SPL account on-chain). The Receive dialog handles this through a chain-specific helper.
- **ICP** — the principal is rederived per token canister.
- **EVM / Tron / Canton** — the same parent address is shown for the token.

### 3.11 validateAddress

Token transfers always use the **chain's native address format**, so `validateAddress` is identical to native. The only nuance: on Solana, a recipient EOA may not yet have an ATA — that's not an address-validation issue (the prepare step adds a `createAccount` instruction).

## 4. UI integration in `cysync-core`

Most of the family-specific UI work was already covered in [how-coin-support-works.md §8](how-coin-support-works.md#8-ui-integration-in-cysync-core). Tokens reuse those same dialogs and contexts; the only token-specific UI surfaces are:

### 4.1 Token icons

[`packages/cysync-core/src/components/CoinIcon.tsx:83-87`](../../../packages/cysync-core/src/components/CoinIcon.tsx#L83-L87) — `TokenToIconMap`. Tokens that ship with a dedicated icon (USDT, USDC, etc.) need an entry here; tokens without a custom icon fall back to a generic.

### 4.2 Add Token dialog

[`packages/cysync-core/src/dialogs/AddToken/context/index.tsx`](../../../packages/cysync-core/src/dialogs/AddToken/context/index.tsx) is the central hub for the "Add Token" flow.

- Lines 159-181 — assemble the `tokenList` shown to the user by concatenating every token-supporting family's coin list (`evmCoinList`, `solanaCoinList`, `tronCoinList`, `icpCoinList`, `cantonCoinList`).
- Lines 217-252 — filter logic for which tokens are visible (vendor-specific exclusions live here).
- Lines 288-310 — `extraData` object: tokens that need additional state (e.g. ICP stores `publicKey`, Canton stores `instrument`) attach it here. The new sub-account gets persisted with this `extraData` blob.

When a user adds an ICP/Canton token, the AddToken context calls `getCoinSupport(family).createAccounts(...)` (or a chain-specific creation path); for EVM/Solana/Tron, adding a token typically just inserts the sub-account row directly because the token discovery is reactive.

### 4.3 Send dialog — token-aware fee accounting

The Send dialog already branches on `account.type`. When `account.type === AccountTypeMap.subAccount`:

- The amount input shows the **token** balance (`account.balance`).
- The fee display shows the **parent native** balance and unit.
- The "Send All" toggle subtracts the token fee model appropriate for the chain (ICP burns from the token; EVM/Solana/Tron deduct from native).

These branches live inside the same family-specific components plugged into `feeInputMap` / `feeInputPropsMap` / `anaInputMap` (see [how-coin-support-works.md §8.2](how-coin-support-works.md#82-send-dialog-always-if-the-coin-can-send)).

### 4.4 History dialog

The history list shows token transactions inline with native transactions for the same wallet. No token-specific UI changes are needed — the `transaction.assetId` field already distinguishes them, and the icon component picks the right icon via `coinToIconMap` / `TokenToIconMap`.

### 4.5 Portfolio

`getCoinAllocations` already returns one entry per `(parentAssetId, assetId)`, so the portfolio table and pie chart render tokens automatically.

## 5. The `IPreparedTransaction` extension for tokens

Token-capable families extend the family's `IPreparedXxxTransaction` with one or two extra fields:

```ts
// Sketch — exact fields differ per family
interface IPreparedEvmTransaction {
  userInputs: {
    outputs: [{ address, amount, ... }];
    gasPrice?: string;
    gasLimit?: string;
    nonce?: number;
    isSendAll: boolean;
  };
  staticData: {
    averageGasPrice: string;
  };
  computedData: {
    output: { address, amount };
    data: string;            // empty for native, ABI-encoded for ERC-20
    fee: string;
    gasPrice: string;
    gasLimit: string;
    gasLimitEstimate: string;
    l1Fee?: string;
  };
}
```

For tokens, the `data` (EVM), `instructions[]` (Solana), or `instrument` (Canton) field encodes the transfer. The decision to treat the transaction as a token transfer comes from `account.type === AccountTypeMap.subAccount` plus `account.assetId`/`account.parentAssetId` — the family looks up the token in `coinList[parentAssetId].tokens[assetId]` to get the contract/mint/canister/instrument details.

## 6. Token JSON generation (`packages/automation-scripts`)

The JSON files in `packages/coins/src/{family}/` (`erc20.json`, `spl.json`, `trc20.json`, `icrc.json`) are **generated**, not hand-maintained. The source of truth is [packages/automation-scripts](../../../packages/automation-scripts/).

### 6.1 Scripts available

[`packages/automation-scripts/package.json:9-31`](../../../packages/automation-scripts/package.json#L9-L31) defines, per family, three scripts:

| Script suffix | What it does |
|---|---|
| `gen-{family}-list` | Build a fresh `{family}-token.json` |
| `{family}-diff` | Produce a diff report (added/removed/changed contracts) |
| `download-{family}-images` | Download token icon PNGs |

Families covered: `erc20` (EVM), `spl` (Solana), `trc20` (Tron), `icrc` (ICP). Canton's `instruments.json` is currently hand-maintained.

### 6.2 The generation pipeline

Each `gen-{family}-list` script lives in `packages/automation-scripts/src/commands/{family}/createNewList.ts` and follows the same shape — see [packages/automation-scripts/src/commands/erc20/createNewList.ts:5](../../../packages/automation-scripts/src/commands/erc20/createNewList.ts#L5) and the shared body at [packages/automation-scripts/src/tokens/index.ts:2](../../../packages/automation-scripts/src/tokens/index.ts#L2):

```
existing  ──┐
JSON list  │
           │
           ▼
   diff vs. CoinGecko platform map
           │
           ▼
   fetch /coins/list?include_platform=true
           │
           ▼
   for missing coin IDs: GET /coins/{id}?market_data=true
     (cached in packages/automation-scripts/.data/coinDetails/{id}.json)
           │
           ▼
   enrich with: market_cap, decimals, image, description, contract addresses per platform
           │
           ▼
   sort by market_cap; fix deterministic property order
           │
           ▼
   write packages/automation-scripts/.data/{family}-token.json
```

### 6.3 Output schema

Every entry in the output JSON has the same shape:

```json
{
  "id": "tether",
  "symbol": "usdt",
  "name": "Tether",
  "market_cap": 165083807079,
  "platforms": {
    "ethereum":             { "contract_address": "0xdac17f...", "decimal_place": 6 },
    "binance-smart-chain":  { "contract_address": "0x55d398...", "decimal_place": 18 }
  },
  "image": { "thumb": "...", "small": "...", "large": "..." },
  "description": { "en": "..." },
  "last_updated_at": "2025-08-14T...",
  "is_custom_coin": false,
  "is_zero_value_coin": false,
  "version": "e9605674"
}
```

The per-family `token.ts` files in `packages/coins/src/{family}/` read this JSON, then build the typed `IXxxToken` objects:

- They walk every entry, skipping those without the family's platform key (`token.platforms[parentId]`).
- They validate `contract_address` and `decimal_place` are present.
- They construct one token object per platform the token exists on (an EVM token like USDT generates 8+ token objects, one for each EVM chain it's on).
- They index by `assetId` (`tokens` map) and by lowercase contract address (`tokensByContract` map).

### 6.4 Refresh workflow

```bash
export COINGECKO_API_KEY=...   # optional; uses free CoinGecko otherwise
cd packages/automation-scripts
pnpm build:cjs

pnpm erc20-diff                # review what would change
pnpm gen-erc20-list            # generate .data/erc20-token.json
pnpm download-erc20-images     # download PNG icons (optional)

# Then copy .data/erc20-token.json → packages/coins/src/evm/erc20.json
```

To force a full refresh, delete `packages/automation-scripts/.data/coinDetails/`.

The diff output (`{family}-diff.json`) is essential when reviewing: it lists `addedContracts`, `removedContracts`, `changedContracts`, and `idChanges` (where a CoinGecko ID was renamed and a `version` suffix was added to keep the assetId stable). Always review before merging the regenerated JSON.
